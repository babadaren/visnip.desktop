# Visnip 图片翻译引擎调整方案

更新日期：2026-09-17

> 自 0.3.1 起，开源发布版只编译本机离线翻译（CMake `VISNIP_ONLINE_TRANSLATION=OFF`），源码不含任何翻译服务地址。下文的云端、内网和混合模式只在自行构建时以 `-DVISNIP_ONLINE_TRANSLATION=ON` 开启。

## 1. 目标与明确边界

桌面截图、标注、贴图保持轻量；完整图片翻译支持云端、内网服务器、本机离线三种部署位置。用户已经明确需要完整离线能力，不将云端设为唯一实现。

当前这次代码调整属于第一阶段（配置、路由和协议边界），不是完整离线引擎交付。Hi-SAM/SAM-TS、Hy-MT、修复模型尚未接入或下载；组件安装和导入按钮禁用并明确提示待接入。不得用旧版联网文字翻译冒充离线，不得用模型文件存在冒充整链路可用。

### 处理位置

| 模式 ID | 设置名称 | 数据流 | 本机模型 |
| --- | --- | --- | --- |
| `cloud-image` | 云端翻译 | 选区图片 -> 配置的云服务 -> 完整译图 | 不要求 |
| `intranet` | 内网服务器 | 选区图片 -> 明确配置的服务 -> 完整译图 | 不要求 |
| `offline` | 本机离线 | 本机工作进程完成整个处理链 | 主动安装完整组件 |
| `local-ocr` | 混合（联网） | 本机 OCR -> 在线文字服务 -> 本机回填 | 兼容旧模式 |

内网模式是明确指定接收方，不是自动判定网络拓扑的安全沙箱；服务器能否访问外网、是否调用第三方，必须由部署管理员明确配置和验证。当前内网允许显式 HTTP/HTTPS 地址，生产建议使用受信任证书的 HTTPS，不忽略证书错误。不自动跟随 HTTP 重定向，内网请求不使用系统代理。内网地址为空时失败，不回退云端地址。

本机离线模式不得上传图片或文字，不发送翻译健康检查或云端预连接，不自动切换在线供应商。用户可以在联网机器上主动下载包，完全断网机器通过文件导入安装。安装行为与翻译时的网络策略分离。

## 2. 第一阶段已落实的代码边界

- 增加 `CloudImage / Intranet / Offline` 模式，保留 `LocalOcr` 作为明确标注联网的兼容选项。
- 旧 `cloud-baidu` 配置迁移为 `cloud-image`，保留旧用户的云端选择；旧 `local-ocr` 不伪装成离线。
- 未知/损坏的已存储模式按禁用联网的 `offline` 处理，不将配置错误解释为云端授权。
- 云端地址和内网地址独立保存，离线模式的网络端点为空。
- 图片请求只允许云端/内网；旧版文字请求只允许混合模式。网络健康检查也检查当前模式。
- 切换处理位置后取消未完成的翻译/探测请求并清理连接缓存；已经发送的数据无法撤回。
- 禁止整图 HTTP 自动重定向到其他接收方；接收自建服务的真实 `provider`，不要求冒充百度。
- 云端/内网继续使用原有完整译图接口及图片大小、编码和结构检查。
- 本机离线不启动旧 OCR 预热，也不进入旧版翻译流程；尚未接入引擎时明确失败。
- 设置页保留已确认的离线组件下载和导入位置，但不能点击，不显示虚假安装状态。

尚未修改线上后端、没有新建服务器实例、没有提交 Git、没有下载大模型。

## 3. 引擎结构（下一阶段实现）

桌面：

```text
CaptureOverlayWindow
  -> TranslationCoordinator
       -> RemoteImageTranslationClient (cloud / intranet)
       -> LocalEngineManager (offline, 独立工作进程)
  <- ImageTranslationResult
```

引擎共享处理流程与结构化数据，各部署可使用不同精度和计算后端：

```text
图像输入与坐标系校验
  -> OCR（文字内容、位置、置信度）
  -> 布局与上下文分组（正文、标题、菜单、表格、控件）
  -> 文字笔画分割、保护区域生成
  -> 上下文翻译（稳定 ID、段落、术语及保留项）
  -> 字体样式估计、可用区域布局求解
  -> 只对成功单元抹除原文并修复背景
  -> 字形绘制、碰撞检查、像素修改范围校验
  -> 完整无损译图、逐单元状态与失败原因
```

三种区域必须解耦：

1. 语义上下文范围：翻译时允许参考哪些段落、标题和相邻控件。
2. 原文字抹除范围：明确属于待替换文字的像素掩膜。
3. 译文布局范围：允许换行或扩展的控件区域，排除图标、边框和其他文字。

大范围上下文不意味着大范围擦除。正文按段落翻译并重新断行；按钮、菜单项和表格单元格保持独立 ID，同时共享上下文。字体估计、译文断行和图标保护不能由 Hi-SAM 单独替代。

## 4. 模型与运行环境策略

- OCR：先保留现有已能运行的模型作为基线，不将升级 OCR 误认为解决了上下文和回填。
- 翻译：Hy-MT GGUF + 匹配的 llama.cpp 程序是候选。最终固定版本、量化、提示模板与验收数据，不追随可变的 latest 标签。
- 分割：按效果/资源验证 Hi-SAM、SAM-TS、Efficient Hi-SAM-S；不要求同时安装 Hi-SAM 和 SAM-TS。
- 常规 Hi-SAM/SAM-TS 权重还可能需要匹配的 SAM 图像编码器权重，组件清单必须完整列出。
- 背景修复：简单背景优先局部算法；复杂背景再评估 LaMa 等模型。无法可靠恢复的区域保留原图并报告，不声称恢复了真实隐藏像素。
- 字体：本机可尝试可用的 UI Automation 属性；纯图像用候选字体重渲染拟合。目标语言缺字时使用许可允许且视觉接近的替代字体。
- Hi-SAM 官方推荐 Linux/PyTorch/CUDA 环境；Windows CPU、CUDA 及其他后端均需单独验证，不能宣称已经适配。

## 5. 离线组件包与导入（尚未实现）

用户入口是一次安装完整离线能力，内部可以拆包以降低重复下载：

- Windows 独立运行环境与依赖库。
- OCR 检测/识别模型、语言字典。
- 翻译模型、词表与提示模板。
- 文字分割模型及其基础编码器。
- 修复模型和非模型修复程序。
- 排版资源、允许分发的字体和许可证。

每包清单至少包含 schemaVersion、包 ID/版本、平台/架构、引擎协议版本、计算后端、支持语言、能力列表、依赖包、各文件字节数/哈希、来源和许可证。发布目录和包须有可验证的信任来源：哈希只能证明文件与清单一致，不能证明清单可信。

安装流程：空间检查 -> 临时目录下载或离线导入 -> 限制解包路径/大小/链接 -> 校验签名及全部文件 -> 检查依赖 -> 合成图片端到端自检 -> 原子激活。失败不替换已有可用版本。不自动执行来自未信任包的任意命令。

离线包必须自包含：不能在导入过程中联网 pip install、下载缺失的 SAM 权重或依赖开发机缓存。运行使用明确本地模型路径，并设置对应推理框架离线参数。环境变量/模型参数不是操作系统网络沙箱；发布前还需抓包或隔离环境测试外联行为。

安装、完整性通过、硬件支持、端到端自检通过分别显示状态，只有最后一个状态才能标记完整离线能力可用。缺少分割/修复能力的轻量模式必须明确降级，不能声称等价质量。

## 6. 工作进程和资源生命周期（尚未实现）

- 主程序普通启动、截图和贴图时不启动大模型进程。
- 用户请求离线翻译才启动引擎；大模型不要直接加载到截图主进程。
- 提供省内存/连续翻译两种策略，默认省内存。空闲阈值作为实现参数，实测后确定。
- 任务取消、超时、崩溃、切换模式、程序退出时清理工作进程及其子进程树。仅停止父进程不算完成。
- 低内存设备可分阶段加载模型，但必须测量反复加载的成本。
- 总资源统计包含主程序、工作进程和推理子进程，不通过拆进程掩盖占用。
- 工作通信优先命名管道/受控 IPC；采用回环 HTTP 时仅绑定回环地址、随机端口和每次启动的令牌。
- 不在命令行、常规日志中传输截图和 OCR 文本。不将云服务 token 放入离线引擎环境。

本次没有承诺具体包体积、最低内存/显存和推理时间；应在指定目标机器上测量冷启动、热任务及峰值资源。

## 7. 协议与图像质量

短期复用现有接口：

```text
POST /v1/image-translate
请求: image_base64, source_lang, target_lang
响应: provider, source_lang, target_lang, blocks, elapsed_ms,
      translated_image_mime_type, translated_image_base64
GET /healthz
响应: status=ok, image_translation={configured, provider}
```

`provider` 是引擎标识，不是必须以 baidu 开头。当前版本保持已存在的响应编码/大小限制。后续增加协议版本和能力协商，不能把任意不相干的 LLM API 地址当作图片翻译接口。

下一版统一返回 requestId、引擎/模型版本、原图尺寸、结果类型、逐单元 applied/preserved/unfit 状态、不可排版原因和耗时。离线 IPC 和远程 HTTP 应保持相同的逻辑结果，但可以使用不同传输编码。

当前兼容客户端仍有 4 MiB 编码图片上限，超限后 JPEG/缩图再放大；本次没有变更这一行为。自建精确回填接口应协商无损上传和原尺寸合成，推理可分块；禁止在没有告知的情况下以缩小图片掩盖能力不足。最终回填以无损格式输出。

## 8. 需要用户确认的四组信息

| 问题 | 暂定建议/不会擅自做的事 |
| --- | --- |
| 服务端工程在哪里，服务器有什么 CPU/内存/GPU，是否必须禁止第三方外联？ | 不猜测后端路径，不修改线上服务。先复用当前客户端协议。 |
| 离线最低目标电脑是否必须无独显可用，常见内存和 GPU 是什么？ | 以 CPU 可用为目标验证，NVIDIA 加速按独立包适配；未测前不承诺性能或完整支持。 |
| 首批必须支持哪些语言与截图场景，可接受何种延迟？ | 建议英文/中文软件界面优先，区分第一次冷启动和后续热任务；语种可按需扩包。 |
| 离线包体积和运行资源的上限是多少，资源不足是否接受明确标注的轻量模式？ | 默认用户主动下载，无公共用户强制大包；不自动牺牲图标/背景保护，也不自动上传云端。 |

这些信息不影响第一阶段配置和隔离改动，但决定模型、分发包和引擎后端的正式选择。

## 9. 验收

第一阶段：重新构建并运行核心、UI、处理模式回归测试。新测试只访问 loopback 测试服务，覆盖端点隔离、配置迁移、设置地址保持、离线拒绝网络、空内网地址、自建 provider、禁止重定向和模式切换取消。它们不是模型效果或完整断网验收。

完整引擎：固定真实截图测试集，包含多行正文、标题、按钮、表格、图标菜单、渐变/纹理背景、不同 DPI。分别记录 OCR、上下文误译、漏译、排版失败、字形/字号偏差、原文字迹残留、保护区域像素差异、冷/热延迟和所有进程峰值资源。

完全离线安装验收必须在断网、无开发工具链、无模型缓存的干净 Windows 环境执行，从离线导入到完整翻译均不得需要外网。模型效果及这类部署验收未通过前，禁止宣布完整离线功能已经完成。

## 10. 核对过的上游资料

### 本次发现的既有字体测试盲区

使用 `QT_QPA_PLATFORM=offscreen` 并显式设置 `QT_QPA_FONTDIR=C:/Windows/Fonts` 后，核心测试有两项失败：

- `fragmentedSingleLineBoxesRecoverFullSentence`：实际 4 个恢复框，期望 2 个。
- `shortLabelDoesNotExpandAcrossNearbyArtwork`：实际应用 1 个回填单元，期望保留原图不应用。

对照运行本次改动前的 Release 核心测试程序（文件时间 2026-07-31 20:34:22）也得到相同两项失败。移除 `QT_QPA_FONTDIR` 后，核心测试发出找不到字体的告警，而这两项却通过。不能将无字体环境的通过当作真实字体/回填质量验收；需要进一步分辨测试样本对字体度量的假设与实际算法缺陷。本次没有为了变绿而修改这两项断言，也未修改 OCR 后处理和排版算法。

本次最终验证：Debug 重新构建成功；按现有字体环境运行 CTest 三个目标全部通过，QtTest 汇总为核心 89 通过、UI 31 通过/5 跳过、处理模式 10 通过（这些计数含初始化/清理）。日志保存到 `build/windows-mingw-debug/translation-modes-regression.log`。随后单独用真实字体重跑上述两项，仍为 2 项失败，日志保存到 `build/windows-mingw-debug/known-font-regressions.log`。真实字体问题没有被删除断言或调整算法掩盖。

相同失败可用以下命令重现：

```bat
set QT_QPA_PLATFORM=offscreen
set QT_QPA_FONTDIR=C:\Windows\Fonts
build\windows-mingw-debug\visnip_core_tests.exe fragmentedSingleLineBoxesRecoverFullSentence shortLabelDoesNotExpandAcrossNearbyArtwork
```
